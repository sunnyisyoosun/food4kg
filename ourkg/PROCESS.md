# 과정 기록 — 절차에서 틀린 것들

이 문서는 **무엇이 틀렸고, 어떻게 드러났고, 무엇으로 막았는지**만 모은다.
결과는 [`RESULTS.md`](RESULTS.md), 데이터는 [`DATA.md`](DATA.md), 방법은
[`METHODS.md`](METHODS.md) 다.

왜 따로 두는가 — `RESULTS.md` 에 섞어 두니 **발견과 실수가 뒤섞여** 둘 다 읽기
어려워졌다(5,200 줄에 정정 기록 100 곳 이상). 그리고 실수의 **유형**이 반복되는데
흩어져 있으면 그 반복이 보이지 않는다.

---

## 한 줄 요약 — 반복된 유형은 하나다

> **실패해도 출력이 그럴듯하다.**

틀린 자리가 비어 있거나 터지지 않고 **그럴듯한 숫자**를 냈다. 그래서 거의 전부
**우연히** 발견됐다 — 다른 작업을 하다 diff 가 떴거나, 로그 한 줄을 봤거나,
사용자가 "다시 확인해 보라" 고 했을 때.

| 어떻게 발견했나 | 건수 |
|---|---:|
| 우연 (다른 작업 중 diff · 로그 한 줄) | 9 |
| 사용자 지적 | 3 |
| **자동 검사가 잡음** | **5** |

마지막 줄이 이 문서의 목적이다. 검사를 넣기 전까지는 **우연에 기대고 있었다.**

## 검사를 **부르는 것**도 자동으로 — `hooks/pre-commit`

검사가 29 항목으로 늘었지만 **부르는 것이 사람 기억에 달려 있었다.** git hook ·
CI · 그 어떤 자동 실행도 없었고, `run_all.py` 의 `check` 단계는 50 분짜리 전체
실행의 마지막이다. 그러면서 `docs` 검사가 내 문서 갱신 누락을 **두 번** 잡았는데
둘 다 내가 수동으로 돌렸을 때였다.

`hooks/pre-commit` 이 커밋마다 `check.py` 를 돌리고 실패하면 **커밋을 막는다**
(2 초). 켜는 법은 `git config core.hooksPath hooks` 한 번.

- 훅을 `.git/hooks/` 대신 레포의 `hooks/` 에 둔다 — git 은 `.git/hooks/` 를
  추적하지 않아 받는 사람에게 안 따라간다.
- `.venv/bin/python` 이 있으면 그걸 쓴다. 전역 python 에는 pandas 가 없다.
- 산출물이 없는 갓 clone 에서는 검사가 전부 SKIP 이고 통과한다 — 커밋을
  막지 않는다.
- 의도한 상태를 커밋해야 하면 `SKIP_OURKG_CHECK=1` 또는 `--no-verify`.

**막는지 확인했다** — `kg_stats.csv` 의 출처 합을 일부러 틀리게 하고
`git commit` 을 시도해 `FAIL KG 통계 정합` 과 함께 **커밋이 생기지 않는 것**을
봤다(최신 커밋이 그대로였다). 되돌린 뒤 29/29 통과.

## 아직 못 막는 것

- **4 번 항목 전부** — 해석의 잘못은 자동으로 못 잡는다. 할 수 있는 것은
  ① 판단을 **질적**이라고 명시하고 ② 가능하면 **규칙으로 세어**(`toperr.py`)
  대조하고 ③ 예측을 **계산 전에 코드에 고정**하는 것(`diet_intervention.
  PRESPECIFIED`)뿐이다.
- **생성 가능성** — `check.py` 는 산출물 정합만 본다. 단계 간 의존이 깨졌는지는
  `run_all.py` 를 끝까지 돌려야 안다(2.6 이 그렇게 나왔다). 50 분이라 커밋
